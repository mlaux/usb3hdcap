staging: media: add driver for StarTech USB3HDCAP
This adds a V4L2 driver for the StarTech USB3HDCAP video capture device,
supporting composite, S-Video, component, and HDMI inputs. It also includes
an ALSA capture device for audio support.

Is this vulnerable to a use-after-free race condition? In
usb3hdcap_audio_data(), the pointer to substream is read, and then
substream->runtime is accessed without holding any locks protecting the
lifecycle. 
Concurrently, snd_hdcap_pcm_close() sets hdcap->snd_substream to NULL
locklessly. If the URB handler is preempted after reading the substream
pointer, the ALSA core could free the runtime structure before the handler
resumes and dereferences it.

Could this result in a use-after-free if the ALSA device remains open?
The usb3hdcap structure is freed when the v4l2_device refcount drops to zero.
However, the ALSA sound card uses this structure as its private data without
holding a reference to the v4l2_device. If userspace closes the V4L2 device
but keeps the ALSA PCM device open, the structure will be freed and
subsequent ALSA operations will dereference it.

Can this sequence result in a heap buffer overflow? If userspace calls
VIDIOC_REQBUFS before the signal is locked, buffers are sized here for SD
video. Later, start_streaming calls usb3hdcap_hw_init which locks the signal.
If a 1080p signal is found, the driver dynamically increases hdcap->height
and hdcap->bpl. When process_video_line later writes the larger 1080p frame
into the smaller SD-sized vb2 buffer, it will write out of bounds.
[ ... ]
> +static void usb3hdcap_stop_streaming(struct vb2_queue *vq)
> +{
> +	struct usb3hdcap *hdcap = vb2_get_drv_priv(vq);
> +
> +	if (hdcap->usb_dev)
> +		usb3hdcap_stop(hdcap);
> +}
Will this leak memory and cause a use-after-free on disconnect? During
disconnect, hdcap->usb_dev is set to NULL. When the V4L2 device is later
released, vb2_queue_release calls usb3hdcap_stop_streaming. Because
hdcap->usb_dev is NULL, usb3hdcap_stop is entirely bypassed. The ISO URBs are
never killed, and the transfer buffers are never freed. The still-running
URBs will eventually invoke their completion handlers and dereference the
freed hdcap structure.
